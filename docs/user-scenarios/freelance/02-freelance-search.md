# Freelance — Полнотекстовый поиск по проектам: `freelance_search`

**Домен:** Фриланс — поиск ранее согласованных условий по пайплайн-файлам
**Длина:** ~4 шага
**Репозиторий:** `trained-assist-freelance-skill` (domain skill server)
**Тул:** `freelance_search(query, project_id?)` — read-only, без LLM и внешних вызовов
**Хранилище:** `$USERS_DIR/<profile>/Фриланс проекты/<project-slug>/` (файлы стадий: `facts.md`, `requirements.md`, `interpretation.md`, `solution.md`, `qna.md`, `spec/*`, `project.json`, `risk-assessment.json`, `provenance/log.jsonl`)
**Охват:** от запроса «где мы согласовали бюджет/сроки?» до списка совпадений с точной привязкой к проекту и файлу

> Ценность (V3 — прямой запрос владельца, issue #53 п.6 из бэклога #50, одобрено 29.09.2026):
> **владелец продукта (через агента) нашёл ранее согласованные условия — бюджет, сроки,
> требования — по всем фриланс-проектам профиля одним вызовом, не читая файлы вручную.**
> Негативная ценность: агент не отвечает «не знаю / давай посмотрю каждый проект» и не
> тащит в контекст десятки файлов, чтобы найти одну фразу.

---

## Контекст (начальный state)

- Профиль хранит N фриланс-проектов в `Фриланс проекты/` (бывает 0 и бывает 10+)
- Соглашения живут в файлах стадий, написанных в разные дни разными вызовами `freelance_add_info`
- Сегодня единственный способ найти фразу — `freelance_get_project` по одному проекту
  или ручное чтение файлов (дорого по контексту, не масштабируется на «по всем проектам»)
- Read-only: поиск ничего не пишет и не меняет

---

## Сценарий

### Шаг 1 — Запрос «где мы согласовали X» по всем проектам

```
User: в каких проектах мы согласовали предоплату 50%?
```

**Ожидаем (EARS):**
- КОГДА агент вызывает `freelance_search({query: "предоплата"})` ТОГДА система
  возвращает массив совпадений `{project, file, line, snippet}` по файлам стадий
  ВСЕХ проектов профиля
- КОГДА поиск выполняется ТОГДА он идёт локально по файлам хранилища —
  без LLM-вызовов и без внешней сети
- КОГДА строка найдена ТОГДА `snippet` содержит найденный фрагмент с контекстом строки,
  `line` — номер строки, `project` — имя/слаг проекта, `file` — путь файла внутри проекта

**Validation:**
- Ответ содержит хотя бы одно совпадение из разных проектов (если фраза есть в двух)
- Ни одного обращения к OpenRouter/сети при вызове

---

### Шаг 2 — Сужение до одного проекта

```
User: а только по проекту Renovatio — там что со сроками?
```

**Ожидаем (EARS):**
- КОГДА передан `project_id` ТОГДА поиск ограничен файлами только этого проекта
- КОГДА `project_id` не существует ТОГДА система возвращает ошибку in-band
  (`isError`, читаемое сообщение «проект не найден»), а не исключение/краш

**Validation:**
- Вызов с корректным `project_id` не содержит совпадений из других проектов
- Вызов с несуществующим `project_id` → in-band ошибка, процесс жив

---

### Шаг 3 — Ответ пользователю с привязкой

```
Agent (ответ): Предоплата 50% — в 2 проектах:
  1. Renovatio МИС — requirements.md:42 «предоплата 50% при старте»
  2. ЖБИ-заводы — facts.md:17 «…»
```

**Ожидаем (EARS):**
- КОГДА агент получил совпадения ТОГДА он отвечает списком с указанием проекта и файла,
  а не пересказывает содержимое файлов целиком

**Validation:**
- В ответе пользователю есть привязка project + file, а не только текст фразы

---

### Шаг 4 — Пустой результат и граничные случаи

**Ожидаем (EARS):**
- КОГДА совпадений нет ТОГДА система возвращает пустой список (`matches: []`),
  без ошибки — «не найдено» это валидный ответ
- КОГДА `query` пустой или отсутствует ТОГДА in-band ошибка валидации
- КОГДА файл нечитаем (бинарник, нет доступа) ТОГДА он пропускается —
  остальные файлы всё равно просканированы, вызов не падает
- КОГДА совпадений больше лимита ТОГДА возвращается обрезанный список с явным признаком
  «показаны первые N», без зависаний

**Validation:**
- Пустой `query` → in-band ошибка
- Несуществующий проект → in-band ошибка
- Поиск по непустому профилю не трогает ничего за пределами `Фриланс проекты/`

---

## Не-цели (сознательно НЕ делаем)

- Семантический/LLM-поиск и ранжирование — только детерминированное вхождение подстроки
- Запись/изменение файлов — тул строго read-only
- Поиск вне хранилища текущего профиля (другие профили, `~/`, сеть)
- Индекс/BM25/поисковый движок — сканирование по запросу достаточно для масштаба профиля
- Пагинация и фильтры по датам/стадиям — вернуть срез, потом уточнять запросом

---

## Крайние случаи

| Ситуация | Ожидаемое поведение |
|----------|---------------------|
| Профиль без проектов | Пустой список, без ошибки |
| Русский текст, разный регистр («Предоплата»/«предоплата») | Совпадение есть — сравнение регистронезависимое |
| Очень частая фраза («клиент») | Обрезка по лимиту + признак «первые N», не OOM |
| `project_id` с попыткой path traversal (`../../`) | Отклоняется резолвером путей, поиск не выходит за хранилище |
| Случайное совпадение в `provenance/log.jsonl`/JSON | Файлы стадий — основной объём; нечитаемое пропускается, вызов не падает |

---

## Проверяемые инварианты

1. **Read-only:** вызов не модифицирует ни один файл в `Фриланс проекты/`.
2. **Без LLM и сети:** при вызове нет обращений к OpenRouter/внешним API.
3. **Изоляция профиля:** поиск не покидает хранилище текущего профиля.
4. **In-band ошибки:** невалидный вход → читаемый объект ошибки, не исключение процесса.
5. **Детерминизм:** одинаковый `query` на одном хранилище → одинаковый набор совпадений.
